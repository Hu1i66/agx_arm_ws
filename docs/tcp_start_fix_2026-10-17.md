# TCP验证起点拦截修正（2026-10-17）

## 现象与依据

用户粘贴运行：plan完成40小段，execute输入确认后报“衔接验证后真实起点移动，须重新规划”。
该错误在本段send_goal_async之前，所以该次执行未能进入运动。
磁盘上的onsite_report较新，记录7段成功后遇到同一错误；保留该记录，不与粘贴那次运行混为一轮。

旧实现guard用一次真实反馈建立计时/检查的衔接，随后execute再读取一次；六轴任一差值超过0.0001rad
即退出，没有等待停稳或重新验证路径。这个门仅约0.00573°。旧错误信息没有保存两次读数差值，
因此不能据此确定当时变化来自余动、反馈更新还是外部运动。

仅订阅实际关节与TCP反馈5秒的观测得到1001个关节消息，当前六轴峰峰变化为零；
这不代表失败当时也为零，也不能据此断言机械臂持续抖动。

## 修正

- 每段衔接前等待至少0.3秒的真实关节窗口，至少3条不同源时间戳反馈，六轴变化范围≤0.0001rad。
- 最长等待3秒；持续运动、反馈过期或源时间戳冻结时拒绝。
- 衔接验证与派发前实际起点仍用原0.0001rad门；发生变化时重新等待、重建、计时并做碰撞/FK检查，最多3次。
- 保存原规划位置列表，重试不会层层累加旧桥接段。
- 超出原规划起点允许范围、路径碰撞、FK失败、中断、参数或候选变化仍拒绝；没有关闭检查或改质量门。
- 新增start_stability_checks和start_revalidation报告字段，记录停稳窗口、六轴变化和前后快照。

修改文件：tcp_verification_ros.py、tests/test_tcp_verification.py、docs/tcp_calibration.md。
没有修改T1、CAN激活、SDK、MoveIt配置、生产抓取或标定参数。

## 操作

保持当前T1运行，关闭T5/T6及其他运动源，将工具点留隙对准并停稳，再运行docs/tcp_calibration.md第7.6节的
原execute命令。无需重启T1、重新激活CAN或重做标定；统一入口直接读取修改后源码。
确认后输入EXECUTE TCP。如上次已运行若干段后停止，重新对点后再启动，程序会以本轮真实起点生成新序列。
若仍失败，新日志会显示具体变化量与重试次数，报告保留诊断值。现场自动运动及真实尖端漂移仍由操作者验证。
