# D455 动态抓取操作与实现说明

更新日期：2026-10-18。状态：完成代码改造和离线分析，等待连接传送带后的现场验收。

出现STM32 I/O错误、CAN失联或TF断开时，先按[USB恢复说明](usb_recovery.md)处理连接；
GUI现在支持STM32后台重连，不会补发旧启动命令。不要用动态抓取参数补偿硬件断线。

## 1. 本次范围

适用于 D455 固定相机、传送带匀速运行、物体随皮带移动的普通水果动态抓取。
Dabai 继续使用已经验证的静止抓取。本次没有启用 Dabai 动态抓取。
STM32 的 `speed` 原值作为速度基准；不乘 `conveyor_calib.json` 中历史 `speed_scale`。
现场实测 GUI/STM32 速度与实际带速的比例在 86%~97% 之间随设定值变化
（0.040→0.0359、0.072→0.0699、0.0324→0.0280 m/s），不能用一个固定比例补偿。
因此到待命位后用正常视觉帧的沿带位移斜率估计真实速度，给本轮预测加沿带残差；
修正限于STM32速度的±20%，不是修改串口值或GUI显示，也不改历史标定。
既有 STM32 程序的速度平滑方式不变。方向文件含有 `motor_direction` 参考位时，
当前方向位与参考位不同时才翻转向量。历史文件没有此字段时，直接使用实测 `dx/dy`，
不能擅自假设参考位为1。当前现场正常输送为画面左→右、基座+Y，STM32返回M2=0。
本次只读观测的同一track在10.64s内Y增加约88.6mm，支持上述方向判断。

当前STM32可能在实际运行、速度为正时仍报告M1=0。因此动态轨迹使用新鲜的正速度，
GUI单独记录收到ACK的启停命令；明确收到停止ACK仍停止本轮。串口断开后清除命令状态，
不自动补发启动命令。这不修改STM32速度数值，也不把M1当作速度。

静止抓取继续读取原来的平滑坐标。新增的 `motion_observation` 只提供动态抓取需要的当前帧质心和图像时间。
它同样使用当前已批准的 D455 内参、手眼和 TCP，不增加 XYZ 手动偏置。

## 2. 新抓取流程

1. 锁定 `motion_session + track_id`，每帧更新同一个物体；不会因为同类水果置信度变化换目标。
2. 先将夹爪张开至95mm目标开口（真实开口以反馈为准），留足移动入爪余量；
   候选状态检查采用张开后的关节状态。
3. **到固定拦截区上方待命**：预定位点的纵向（沿带）坐标固定在
   `intercept_s_pref_m ± intercept_window_m` 内（默认 -0.25±0.07 m），横向跟随物体当前 X，
   高度为 `pregrasp_m`（默认 180 mm）。待命点不再用“物体未来 N 秒的位置”推算，
   预定位耗时或预测误差不会把目标推向下游工作区之外。
   抬高到 180 mm 后，夹爪在物体正上方时不再挡住 D455 对物体的视线，
   只有最后约 100 mm 的下降阶段会短暂遮挡。
4. 待命后重新取新鲜观测，用视觉沿带斜率修正 STM32 速度；
   然后等物体进入可抓窗口（`s_at_start` 落在窗口内）再生成同步轨迹。
   物体已经越过窗口上界时本轮直接放弃，不追到工作区外；
   一直没进入窗口超过 `max_wait_s` 也放弃，避免长时间占住机械臂。
   窗口内使用静止抓取验证过的倾角/短轴选择，深入量按 20→15→10→5→0 mm 回退。
   始终保留源图像时间戳；目标位置由观测点与修正后的速度预测，
   高度跳变或位置突跳帧忽略；派发后视觉只作诊断，不重写在途轨迹。
5. 生成带未来启动时间的接近轨迹：高位平滑对齐，然后在物体随动坐标系内沿工具+Z接近。
   由于已经在待命位就位，对齐段只需消除窗口内几厘米的残差，
   不再承担“从待机位追赶几十厘米”的任务，这也是关节限速失败大幅减少的原因。
6. 在接近结束时发送夹爪闭合目标；机械臂继续随皮带移动，等待夹爪闭合完成。
7. 在同一轨迹末段抬起7cm并平滑降至零速，随后走 MoveIt 放置；到达放置位成功后才松爪。

整条接近/闭合随动/抬起轨迹只有一次机械臂 action 下发，不逐段取消和重发。
各点提供位置、速度和明确时间，不再插值后重新均分时间。
使用解析三次样条极值检查速度和加速度；需要放慢时重新预测物体位置、重算IK，不能只拉长旧轨迹。
同一求解轮固定绝对启动时刻；加速度仅延长超限阶段，速度超限采用保守比例。
不会因为对齐阶段超限，就把原本可行的整个下降过程反复放慢。只有计算已耗尽发送时间窗，才重新安排启动时刻。
按控制器实际曲线密采样进行碰撞/限位检查，并保留自碰撞和环境碰撞检查。

该实现是“派发前正常观测修正位置、执行中按速度预测随动”，不是每帧重发机械臂目标的视觉伺服。
运动观测先按STM32速度对齐到同一图像时间，再取短窗口中位数校正XY，避免普通平均造成滞后。
保留被使用观测的图像时间戳，不将预测位置伪装成新视觉测量；STM32状态与真实关节反馈的新鲜度检查保持。
本轮结束后解除锁定，下一物体重新取观测。
物体打滑、滚动、传送带明显变速时，预测会失准；速度/方向明显改变时会取消本轮。
不保证任意带速下都能抓取；速度越快，预定位和计算等待期间占用的工作区越大。

## 5. 现场首次验证

1. 先确认当前静止抓取仍正常，使用 D455、水果模式，关闭其他自动任务及排队执行。
2. 连接传送带，确认界面速度与实际启停对应。第一轮使用容易夹持的圆形物体，放在中间可达区。
3. 从过去能运行的低带速开始，点击“动态抓取”。本次不要求修改速度比例。
4. 观察接近过程中姿态是否保持、夹爪闭合时是否仍跟随；查看日志最终采用的倾角、深入量及报告。
5. 每次只调整一项，确认中间区域可用后再扩大抓取位置和提高速度；随后验证长条物体。
6. 若持续滞后，先分析报告中的图像年龄、计划启动时间、关节跟踪误差和闭合时刻，
   不先添加经验提前量或修改手眼参数。

“停止动态抓取”沿用正常停止：等待在途任务结束再停带。
需要立即停止时使用已有急停按钮；新动态模块会取消本轮机械臂和夹爪目标，不追加回零、回待机或松爪。
单轮失败（IK无解、规划未收敛、空抓、戳碰等）只放弃本轮目标：机械臂停在现场，
传送带与动态模式继续，等下一个物体进入跟踪区再抓；不再因为一次失败关闭动态模式。
连续失败达5次才交回GUI空闲等待（仍不关闭动态模式）。已失败的track不会被GUI原地重发。
漏抓越线后的既有停带处理仍保留；它与“执行失败后跳过”是两条不同路径。
正常放置后允许继续抓取新track，同一命令内不会重复尝试已处理track。
暂时无物体时，动作端交回idle，由GUI已有检测循环继续等待；动态模式与传送带不因空场景退出。
等待期间停止按钮仍正常响应，不让服务端长期占busy。空场景结果标记`waiting_for_target=true`，不伪造一次成功抓取。

## 6. 参数与含义

参数文件：`config/dynamic_grasp.json`，T5每次动态尝试读取，不需要重启T1。

| 参数 | 默认值 | 含义 |
|---|---:|---|
| `pregrasp_m` | 0.12 | 待命/预抓取高度（沿工具轴）。0.06 挡视线，0.18 把手腕逼到极限，0.12 两者兼顾 |
| `extra_depth_m` | 0.02 | 相对质心额外深入，复用20→15→10→5→0mm退让 |
| `align_s` | 0.55 | 高位对齐并平滑接入皮带速度；0.35 时补 1.6 cm 残差就顶到加速度上限 |
| `approach_s` | 0.9 | 从待命高度下降到夹持深度的名义时间（0.20 m / 0.9 s ≈ 0.16 m/s） |
| `close_s` | 0.6 | 夹爪闭合目标时长 |
| `follow_s` | 0.8 | 接近结束后的闭合随动时间，至少比close_s长0.1s |
| `lift_s` / `lift_m` | 0.65 / 0.07 | 随动抬起的名义时间与抬升高度 |
| `sample_s` | 0.06 | 原始IK采样间隔；控制曲线额外按20ms密采样核查 |
| `velocity_scaling` / `acceleration_scaling` | 0.55 / 0.55 | 复用项目关节限值的运行比例；同时用于 MoveIt 的待命移动和放置移动 |
| `send_margin_s` | 0.25 | 预留检查结束到控制器接收的时间 |
| `intercept_s_pref_m` | -0.25 | 拦截区中心（沿传送带方向的基座坐标，当前带向为 +Y，所以是负值） |
| `intercept_window_m` | 0.07 | 拦截区半宽；待命点固定在此范围内 |
| `intercept_s_max_m` | +0.15 | 硬件可抓上界：夹爪闭合那一刻物体最远能到 +0.15 m；更远交给停带静态抓取 |
| `max_trajectory_s` | 4.0 | 轨迹总时长上限；超过说明物体已被拖出可达区，直接放弃 |
| `stage_move_s` | 3.0 | 预估从待机位到待命位的耗时，用于把待命点提前放到物体将到达的位置 |
| `max_wait_s` | 10.0 | 在待命位等待物体进入窗口的最长时间，超时放弃本轮 |

名义接近/随动/抬起时间为2.80s，不含预定位、规划和发送前等待。
关节速度/加速度受限时会重算时间，最终以报告为准，不能把2.80s当作固定实机周期。
闭合不足时先核对夹爪反馈，可增加close_s和follow_s；不要只增加机械臂等待时间而停止随动。
减小approach_s不一定更快：超过关节限制会触发重新计时。

**怎么调拦截区**：`intercept_s_pref_m` 用基座坐标里的沿带距离表示，
当前传送带方向是 +Y（`conveyor_calib.json` 的 dy≈0.9995），所以物体位置约等于 Y 值。
台上能稳定抓到的一段约 -0.32 ~ -0.18 m；如果物体总是"太远够不到"，
把中心往 0 方向（更靠近机械臂）调 0.03 m；如果总是"来不及"，往负方向调。
每次调整后只改这一个数，`intercept_window_m` 保持 0.07 m。

## 7. 报告和故障定位

每次尝试保存到 `data/diagnostics/dynamic_grasp/<时间>_<编号>.json`：

- 锁定的相机会话/track、参数快照、当前帧观测、STM32原始速度向量、视觉拟合速度。
- `motion_speed_estimate`：原速度、观测沿带速度、单轮残差和最终预测速度；`velocity_mps`为实际用于轨迹的预测向量。
- 倾角、深入量、重算次数、计算耗时、未来启动时刻、闭合派发时刻。
- 航点时间、目标位置、关节轨迹、内部模型TCP反馈、位置跟踪偏差。
- 完成/失败原因、取消应答、夹爪宽度。
- `initial_velocity_mps`、`direction_calibration`、原始方向位/M1和命令确认状态。
- `preflight`：各候选的倾角、深入量、IK/碰撞失败阶段；碰撞响应可用时保存接触体和穿透深度。
- `previews`：移动路径预解的重算时间、倍率与具体IK失败原因。
- `stage_target_m` / `stage_s_m`：本轮待命点的三维坐标与沿带坐标；`intercept_window`：进入窗口时的s值与上下界。
- `locked_anchor` / `prediction_mode`：本轮锁定的源图像时间及三维中心、采用的预测方式。
- `last_visual_observation_after_lock`：锁定后收到的最近视觉观测，供比较预测误差。
- `position_updates`：派发前采用的XY修正量、样本数量与源图像时间。
- `last_ignored_observation`：被高度/位置一致性过滤忽略的观测，忽略后继续模型预测。
- `planning_inputs`：每次计算开始时的目标锚点、真实关节角/TCP、速度、时间、有效参数及速度/加速度峰值；IK失败也保存。
- `gripper_open_target_m` / `gripper_open_feedback_m`：张爪目标与实际反馈。
- `gripper_final_feedback`：抬起后的实际宽度、力矩反馈和接收年龄；空抓、无反馈、反馈过期分别说明。
- `feedback`中的`gripper_width_m`：随动过程的夹爪开口，供闭合时序分析。

内部TCP反馈由真实反馈关节角和同一机器人模型计算，只能说明内部跟踪与模型一致性。
报告明确标注“未完成物理精度验证”，现场视频或外部测量才是物体实际抓取偏差的证据。

| 提示 | 处理 |
|---|---|
| 缺少track/session或当前帧观测 | 重启新版T3、T5、T6，避免混用旧节点 |
| 方向/速度不可用、状态过期 | 连接传送带并检查STM32串口数据；不要伪造速度 |
| 真实关节反馈过期 | 检查T1与CAN，使用`/feedback/joint_states`，不能用控制命令冒充反馈 |
| 完整移动路径不可达 | 先将物体放回中间区域，降低带速；查看是否规划等待占用了过多可达范围 |
| `动态轨迹N次规划均未通过(...)` | 括号内是真实原因：加速度超限看 `peak_acceleration/amax`；时间窗看 `prepare_s`；视觉修正看D455是否被挡 |
| 空抓 | 根据视频与报告区分XY预测、深入量和闭合时间问题 |
| 执行/夹爪失败 | 跳过本轮目标，动态模式与传送带继续等下一物体；机械臂保留现场位置，不自动回零或松爪 |

### 2026-10-18 方向及候选耗时修复

本次失败的首要原因是旧方向文件无M2参考位，新代码却默认参考位为1，
把现场M2=0的正常+Y输送预测为−Y。已改为保留历史实测向量。
另一个因素是2cm深入方案可能碰台面，耗时预解顺序导致等待过久。

以失败报告中的位置、假设带速0.06m/s及2s预定位预测作只读重建：

## 11. 单轮失败不再关闭动态模式（2026-10-18 晚）

现场现象：一次IK无解或规划未收敛后，GUI直接进入STOPPING并停带，必须重新点“动态抓取”，
而这段时间里后续水果已经越过跟踪区。

改动：

1. 失败只放弃当前目标。动作端把该`track_id`记入`attempted_tracks`，日志输出
   `动态本轮失败（n/5）：<原因>；已放弃该目标，继续等待下一物体`，随后在同一`sort_dynamic`
   里继续挑选下一个候选（通常是更靠上游、仍可达的物体）。
2. 结果消息新增`attempt_failed`和`failed_track_ids`，`ok`仍为true表示动态模式健康。
   GUI只在`ok=false`（视觉会话变化、急停等）时停止派发；单轮失败保持RUNNING和传送带运行。
   GUI把失败track加入跳过集合，避免200ms一次地原地重发同一个物体。
3. 连续失败达5次（`DYNAMIC_MAX_ATTEMPT_FAILS`）返回idle让位，仍不退出动态模式；
   下一物体越过触发线会重新派发。成功一次即重新计数。
4. 对齐阶段时长改为按“当前TCP→预抓取点”的距离计算（`set_align_time`，0.3m/s、上限1.2s）。
   原来固定0.35s，机械臂从待机位远距离起步时会被关节限速放大约2倍，整条轨迹被拉长，
   水果在拦截前又前移十几厘米，日志表现为`动态IK无解 t≈4.1s`或`规划时间未收敛`。

失败后的机械臂仍保留现场位置，不自动回零、不追加退回或松爪；需要复位时用GUI的
“一键回到待机位并关闭夹爪”。

现场验证要点：

- 连续供料时故意让一只水果在末端失败，确认日志出现“继续等待下一物体”且GUI仍在动态模式、传送带不停。
- 下一只水果进入触发线后应自动派发，无需再点按钮。
- 检查报告`plans[].effective_settings.align_s`，远距离起步时应大于0.35s且倍率接近1。

## 12. 遮挡与“要不要加腕上相机”（2026-10-18）

现场现象：机械臂一到预抓取位，D455 就看不到水果；之后只剩按速度外推，
预测点被推到 `y=+0.30 m` 这类工作区外的位置，表现为`动态IK无解`或`规划时间未收敛`。

根因有三个，跟相机数量无关：

1. 旧 `pregrasp_m=0.06` 让夹爪停在物体上方 60 mm，几乎与物体同高，正好挡住视线。
2. 旧预定位点用 `anchor + velocity*(now + hover)` 追“几秒后的位置”，
   而 `_dynamic_hover_s` 只在每次移动后写一次、从不重置，越积越大；
   一段慢移动之后，后续每次都会追到十几厘米之外。
3. 目标选择固定取最下游的物体，等于每次都挑最接近离开工作区的那个。

本次改为“固定拦截区待命 + 窗口内同步下降”，三个问题同时在软件上解决：
待命高度 180 mm，夹爪在物体正上方时不再挡住 D455；待命点纵向固定，
不再随时间漂移；目标选择只保留还没越过窗口上界的物体。

**结论：暂不需要加腕上相机。** 现有 Dabai 已经是眼在手上（装在末端），
真要在手眼被遮挡时补一次近距离观测，应该先用它，而不是再加一台新相机。
新增相机还要再处理安装刚性、手眼标定、时间同步、曝光和延迟五项误差，
成本远高于先把待命高度和拦截时序调对。等这一版在传送带上连续跑通、
仍然出现“物体进入夹爪后仍有明显横向偏差”时，再评估腕上相机。

现场验收顺序：

1. 先只开传送带，不放物体，点“动态抓取”，确认机械臂停在拦截区上方
   约 180 mm、不遮挡 D455 画面，日志出现`动态预测速度: STM32=..., 视觉=..., 修正=...`。
2. 放一个水果，确认日志先出现“到拦截区上方待命”，
   再在物体接近时出现同步下降；报告里 `intercept_window.s_at_start` 应在 ±0.07 m 窗口内。
3. 连续供料 10 只，统计成功次数；失败时看报告里的 `stage_target_m` 与
   `intercept_window`，判断是“没等到窗口”还是“窗口内预测偏了”。

## 13. “总是求解失败”的原因与修复（2026-10-18 深夜）

上一版上线后仍大量出现`动态规划时间/关节限速未收敛，未派发`和`目标已越过可抓区`。
查看 `data/diagnostics/dynamic_grasp/*.json` 的原始数值后，原因有三条，与手眼/TCP 无关：

1. **对齐段加速度贴边**。报告里 `peak_acceleration` 已达 1.44~1.46，而
   `acceleration_scaling=0.3` 对应上限正好 1.50。待命点与物体差 1.6 cm 时，
   0.35 s 内补完这段的加速度需求就顶到上限，任何抖动都会判超限。
2. **失败重试越修越远**。每次重算约 0.4 s，物体又前进 1 cm；下一次要补的距离更大，
   加速度再次超限，`slower()` 把 `approach_s` 一路撑到 7 s 以上，最终 6 次都无法派发。
   旧代码把这类耗尽统一报成“关节限速未收敛”，容易误判成 IK 问题。
3. **待命点没算观测滞后**。`stage_target` 只用 `移动耗时` 外推，
   忽略“图像时刻到现在”的间隔（本例约 2.3 s）。待命点整体滞后，
   移动结束时物体已越过窗口，表现为 `s=-0.117 > hi=-0.136`。

对应修复：

| 项 | 旧 | 新 | 作用 |
|---|---|---|---|
| `align_s` | 0.35 s | 0.55 s | 同样残差下加速度需求降到约 40% |
| `acceleration_scaling` | 0.3 | 0.45 | 上限 1.5→2.25，瞬时几何变化不再判超限 |
| `max_plan_attempts` | 6 | 4 | 减少“失败后物体又走远”的累积 |
| `stage_target` | 只加移动耗时 | 观测滞后 + 移动耗时 | 待命点落到物体真实将到达的位置 |
| 规划提前量 | 上次耗时 + 0.25 s | `max(0.8, 上次耗时×1.5+0.4)`，上限 2.2 s | 不再卡在发送时间窗边上 |
| 单阶段放慢 | 一次最多 ×3，无上限 | 一次最多 ×1.5，总长 ≤ 配置值 2.5 倍 | 避免 `approach_s` 被撑到 7 s |
| 视觉修正重算阈值 | >3 mm 就整条重算 | >8 mm 才重算，其余由对齐段吸收 | 避免每 0.4 s 重算一次 |

失败信息也改成能直接定位的写法，例如
`动态轨迹4次规划均未通过(关节速度/加速度超限(倍率1.46))`、
`(规划耗时1.20s超过发送时间窗)`、`(视觉修正12.3mm)`。
看到括号里的原因就知道该调时间还是该查视觉。

现场验证：若仍偶发超限，先看报告 `plans[].peak_acceleration` 与
`settings.acceleration_scaling` 的比值；若比值长期 >0.9，再把 `acceleration_scaling`
提到 0.55，不要直接改 `intercept_s_pref_m`。

## 14. 部分物体没被抓、规划慢（2026-10-18 23:40 后）

   该行为只对动态待命位启用（`depth_ladder=True`），静止抓取的选序不变。

另外，停带后的兜底从 GraspNet 改回质心静态抓取。GraspNet 依赖 T4 服务，
未启动时要等 15 s 超时才跳过（日志中的`GraspNet 失败 (timeout_15.0s)`全是这个原因）；
而质心 + 短轴这条路本来就是现场验证可用、你手动点“从检测坐标夹取”用的同一条。

待命移动的 MoveIt 规划时间从 3 s×3 次收到 2 s×2 次，减少无谓等待。

现场观察点：

- 日志不再出现大段`预抓取IK失败`刷屏；同一轮一般 2~3 行就通过。
- 物体只要没越过 GUI 蓝色放弃线，就应该进入“到拦截区上方待命”。
- 若仍出现`目标来不及(到位时s=...)`，说明物体在待命移动完成前就会越过 -0.06 m，
  属于真的来不及；此时降低带速或提前放料，不要放宽 `intercept_s_max_m`。

## 15. 动作看起来“走一段→停一会→再抓”（2026-10-19）

现场观察到的两段式动作来自 14 版的设计：先到拦截区上方待命，再在原地等物体进入窗口。
看上去就是“飞过去、停住、再下降”。本次把等待挪到移动之前，动作变成一次连续到位：

1. 规划算完就调用 `delay_for_intercept`：按物体到窗口下沿的时间减去一次待命移动耗时，
   先让机械臂停在上一位置等，物体快进窗口时才开始移动。
2. 到位后 `wait_in_window` 通常直接通过（剩余误差很小），随即进入同步下降。
3. 对齐段不再固定 0.55 s：残差 ≤3 cm 时用 0.30 s，只有大残差才拉长到 0.4~1.4 s；
   若 `slower()` 因关节限速主动拉长过，则保持拉长值，不会被自适应缩回去。

报告里新增 `pre_wait_s`（移动前的等待时长）。现场判断方法：

- `pre_wait_s` 有值、日志出现`等待目标接近N.s，随后一次走到位`：属于正常的前置等待。
- 到位后仍明显停顿：看 `plans[].prepare_s`，这是规划耗时；再看 `lead_s - prepare_s`，
  这是预留的发送余量。两者之和就是停顿时间。
- 若物体已经在窗口内，`pre_wait_s=0`，机械臂立即开始移动。

注意：不能把“待命移动”和“下降”合成一条轨迹。下降轨迹要求从预抓取点起步，
若从放置点直接连到物体，0.6~0.8 m 的横向位移要在 1.4 s 内完成，
会远超关节限速并被拒绝。分成“快速到位 + 短对齐 + 下降”是当前最稳的形式。

### 补充：限速抖动与更靠下游的物体（2026-10-19）

- 关节限速判据从 `>1.001` 放宽到 `>1.03`。限值本身已按 45% 缩放，3% 余量仍远低于
  电机真实上限；日志里出现 `1.0 → 1.09` 来回抖动时，再重算一次只会让物体多走 1 cm。
- 规划尝试次数 4 → 6，`intercept_s_max_m` 从 -0.06 放到 -0.02 m，
  给“稍远一点”的物体多留 4 cm 动态拦截余量。
- 物体放到 `s≈+0.02 m` 时仍会被判`目标来不及`：那已经越过机械臂能闭合的位置，
  不是参数问题。这类物体应交给“停带到 490 线后静态抓取”的兜底路径。

### 真正的停顿来源：待命点没对准“轨迹启动时”的位置（2026-10-19）

报告 `20261019-000959` 的实测数据：待命点 `s=-0.259`，但轨迹启动时物体已经在 `s=-0.210`，
对齐段要硬补 6 cm，倍率 2.04→1.30→1.13 连算三次，机械臂就停在原地约 2 秒。

原因：`stage_target` 只预测到“移动结束”的物体位置，却漏掉了随后的规划提前量
（`lead≈0.8~1.0 s`，物体又走 2.5~3 cm）和规划本身的耗时。修法：

1. 待命点改为对准“轨迹启动时”的位置：`s_now + v*(观测滞后 + 待命移动耗时 + 规划提前量)`。
   同一组数据回算，待命点由 -0.259 变成 -0.109，正好压在物体将到的位置，对齐残差≈0。
2. 等待下沿从 `待命点-7cm` 收到 `待命点-3cm`，避免刚进窗口就起步、把残差重新拉大。
3. 规划提前量从 `prepare×1.5+0.4`（约1.05 s）收到 `prepare×1.2+0.3`（约0.83 s）。
4. 去掉与 `plan()` 重复的整条轨迹预解（`preview_candidate`），省约 0.4 s。

到位后残余停顿 ≈ `lead - 规划耗时`，目前约 0.3~0.4 s，属于控制器接收余量，不能再压。
`intercept_s_max_m` 同时从 -0.02 放到 +0.05 m：之前 `抓取点s=+0.010m` 被判越界，
现在会真的去抓；只有真够不到时才会由 IK 明确报错。

### 为什么明明够得到还会被判“超限”（2026-10-19）

报告 `20261019-001646` 的峰值数据显示：速度最高只到限值的 0.93 倍，
但 3 号和 5 号关节加速度到了舒适限值的 1.7~2.1 倍。舒适限值 = 硬件限值 × 0.45，
也就是说这条轨迹只用了硬件能力的约 94%，本来完全做得动，却被“舒适阈值”丢掉。

三处修正：

1. **硬件限值兜底**：超舒适阈值但仍在硬件真实限值（速度/加速度各留 2% 余量）内的轨迹，
   照常执行，只在日志给一条`超舒适限值(倍率x)但未超硬件限值`警告，并在报告
   `hard_limit_accepts` 里留档。只有真的破硬件限值才放慢重算。
2. **对齐时长按加速度反推**：静止到静止补 d 米的加速度约 `6d/T²`，改用 `T=sqrt(6d/1.2)`，
   不再用固定 0.3 s 下限。3 cm 残差由 0.30 s 变为 0.39 s，6 cm 变为 0.55 s，
   从源头降低峰值，而不是事后重算。
3. **轨迹采样加密**：`sample_s` 0.06 → 0.045 s，三次样条在转角处的加速度尖峰更小。

判断方法：如果日志出现`超舒适限值...按硬件限值执行`，说明动作仍在硬件能力内；
若连硬件限值也超，才会看到`关节速度/加速度超限(倍率...)`并放弃本轮。

### 失败时“重新就位再解”，不要原地死磕（2026-10-19）

报告 `20261019-002142` 的记录：六次原地重算，对齐时长 0.30→0.47→0.54 s，
关节 5 加速度从 24.9 降到 5.3 rad/s²，第五次又弹回 7.6。
原因是机械臂一直杵在原地，物体却持续前进，要补的距离每次都更大，永远追不上。

改动：

1. 单次抓取最多两轮待命（`max_stage_rounds=2`）：第一轮规划失败后，机械臂按物体
   **新位置**重新移动到待命点再解一次；第二轮不再复用上一轮倾角，整套倾角重新扫描，
   有机会换一个避开手腕奇异的姿态。日志会打印`重新待命(第2轮)`与`动态规划未通过，重新就位后再试`。
2. 对齐时长系数由 1.2 降到 0.3 m/s²：手腕把 TCP 加速度放大约 20 倍，
   2.3 cm 残差用 0.68 s 而不是 0.30 s，关节 5 从 24.9 rad/s² 降到约 6。
3. 单阶段放慢上限从 2.5 倍放到 3.5 倍：0.2 m 下降用 3.15 s 时腕关节约 2.7 rad/s²，
   能稳定落回硬件范围内。

两轮都失败才放弃该物体；此后它基本已走出可抓区，继续等下一个是合理的。

## 16. IK 无解的真正原因：预抓取高度 18 cm 把手腕逼到极限（2026-10-19）

日志里 5 次失败都是同一句：`动态IK无解 t≈1.1~1.4s xyz≈[0.30,-0.06,0.18]`，
即**物体正上方 18 cm 的预抓取点**解不出 IK。用生产同一套 Pinocchio 模型离线扫描：

| 预抓取高度 | 该点可行倾角 |
|---:|---|
| 0.18 m | 只有 15°、20°、25°、30° |
| 0.15 m | 10° 起 |
| **0.12 m** | **5° 起** |
| 0.10 m | 0°（垂直）也可行 |
| 抓取高度 0.01 m | 全部倾角可行 |

结论：物体本身完全够得到（降到抓取高度全部可解），是“18 cm 高度 + 固定倾角”把
手腕顶到关节极限。18 cm 是上一版为避开 D455 遮挡定的，代价过大。

改动：

1. `pregrasp_m` 0.18 → **0.12 m**。此前失败的点 `(0.289,-0.058)`、`(0.303,-0.078)`、
   `(0.307,0.011)` 现在在 5°~30° 倾角全部有解。下降行程同时由 0.20 m 缩到 0.14 m，
   加速度需求再降 30%。
2. 缓存姿态增加**径向偏航校验**：姿态是按上一个物体的径向方向生成的，
   物体换方位后偏航角偏差超过 12° 就重新扫描。报告 002923 的失败正是复用了错误偏航角。
3. `velocity_scaling` 0.3 → **0.4**（速度上限 1.5→2.0 rad/s），
   给整条轨迹多留速度余量，减少因速度触发的放慢。

如果现场发现夹爪重新挡住 D455（物体在画面里被夹爪遮住），再把 `pregrasp_m`
调到 0.14~0.15，并接受倾角扫描会多试几次；不要回到 0.18。

## 17. 提速后的失败分析（2026-10-19，带宽 0.048 m/s）

这一轮 18 次尝试里 13 次成功，失败 5 次，分三类：

| 现象 | 数值 | 原因 |
|---|---|---|
| `越过可抓区` ×2 | 抓取点 `+0.067` / `+0.051` vs 上限 `+0.050` | 只超 1~17 mm，是阈值卡太紧 |
| `来不及` ×1 | 到位时 `s=+0.125` | 物体在移动途中就已越过 |
| `动态IK无解 t=6.18s` ×1 | `xyz=[0.46, 0.21, 0.052]` | 轨迹被放慢到 6.2 s，物体又走了 29 cm，横向 0.46 m 处确实够不到 |

离线核查（同一 Pinocchio 模型，x=0.33）：

| 物体 y | 预抓取高度 0.12 m | 抓取高度 0.01 m |
|---:|---|---|
| +0.05 ~ +0.17 | 5°~30° 全可行 | 全部倾角可行 |
| +0.20 | 10° 起 | 全部可行 |

说明纵向 +0.15 m 以内都够得到，真正到不了的是**横向 0.46 m** 那种。

对应改动：

1. `intercept_s_max_m` +0.05 → **+0.15 m**，那两次“超 1~17 mm”不再误杀。
2. 新增 `max_trajectory_s=4.0`：轨迹一旦超过 4 s 直接放弃并打印
   `动态轨迹过长(6.2s > 4.0s)`。带宽 0.048 m/s 时每多 1 s 物体就多走 4.8 cm，
   6 s 的轨迹注定追不上，硬算只会浪费时间。
3. `velocity_scaling` 0.4 → **0.55**，`acceleration_scaling` 0.45 → **0.55**。
   这两个值同时作用于 MoveIt 的待命移动和放置移动，是整个循环提速的主要来源。

注意：下降段（0.14 m）的快慢受手腕加速度真限制约，不能单纯缩短 `approach_s`。
日志里的“按硬件限值执行”说明下降已接近硬件能力；再快就要牺牲精度或冒超限风险。

## 18. 循环提速与“空场回准备位”（2026-10-19）

带宽 0.048 m/s、约 15 次尝试的成功率已经不错（失败 3 次：1 次待命位不可达、
1 次超阈 2.3 cm、1 次空抓）。要适应更密的物料，瓶颈不在单次抓取，而在循环里的空转。

实测一个成功循环：

| 阶段 | 耗时 |
|---|---:|
| 闭合 → 开始放置 | 1.5 s |
| 放置移动 + 开爪 | 2.5 s |
| 报告 → 下一次待命（含GUI派发、开爪等待、规划） | 2.5 s |

优化：

1. **放置移动提速到 0.8**：`move_joints` 新增 `scaling` 参数，放置点远离皮带、路径固定，
   用 0.8 的关节限值比例执行（原来是全局 0.55）。
2. **待命移动提速到 0.7**：只影响跨越工作区的那段，末段仍然由同步轨迹接管，不影响精度。
3. **省掉重复开爪**：上一轮放下后夹爪本来就是张开的（宽≥88 mm 且反馈新鲜），
   新一轮不再重复发一次 0.65 s 的开爪动作。
4. **空场回准备位**：一次 `sort_dynamic` 里没有下一个目标时，机械臂先回到上一轮的
   待命关节（`_dynamic_ready_joints`）再交回 GUI。下一个物体越线时，机械臂就在皮带上方，
   不需要再从放置点长途飞过来。

注意：空场回准备位只在**确认没有下一个目标**时执行，不会插在连续抓取之间，
因此不会延迟眼前的物体。

还可以继续压的余量（按需再调）：

| 位置 | 现状 | 可调方向 |
|---|---|---|
| `send_margin_s` | 0.25 s | 降到 0.20 可省 0.05 s，但发送窗更紧 |
| 规划提前量 | `prepare×1.2+0.3` | 规划稳定后可降到 `×1.1+0.25` |
| `close_s` | 0.6 s | 夹爪实际闭合更快时可降到 0.5 s |
| 放置后的开爪等待 | 0.65 s | 若与回程移动重叠可再省，但需要确认不会夹着物体拖动 |
